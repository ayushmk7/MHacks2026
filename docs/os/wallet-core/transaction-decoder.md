# Transaction decoder

The rules by which the badge decides whether a byte string is a payment it is willing to show and sign, with the implementation in full.

- Audience: firmware engineers.
- Status: design, not yet built on hardware. The decoder itself is written and host-tested.
- Base: Solana OS, directory `firmware/solana-os/` at commit `812b8c7` of the [upstream repository](https://github.com/spacemandev-git/solana-defcon-badge-26/tree/812b8c7aca5c366d18c0b040fafd2999f7204d84/firmware/solana-os). Upstream contains no transaction code at all [UPSTREAM: no match for `rpc`, `blockhash` or `lamport` under `src/`]; everything in this document is [OURS].

"host-tested" in this document means: `sol_tx.c` and its tests were compiled with `cc -std=c99 -Wall -Wextra -Wpedantic -O2` and run on a development computer, against byte vectors generated by `@solana/kit` and `@solana-program/token` (the libraries the dashboard uses), and printed `all sol tests passed`. It has not been compiled for or run on the ESP32-S3.

The decoder checks **structure only**. Whether the payer is this badge, whether the token is ours and whether the amount is allowed are policy, decided afterwards by the [signing gate](signing-gate.md#policy-checks).

## Message format

A Solana transaction on the wire is a list of signatures followed by a **message**. The message is what gets signed. The badge API takes the message, not the wire transaction (decision D5 in the [overview](../architecture/overview.md#decisions)): both start with the byte `0x01` for a one-signer transfer (one signature in the wire form, one required signature in the message header), so accepting either would be ambiguous.

Facts about the format are external; sources: [Solana transaction documentation](https://solana.com/docs/core/transactions) and the bytes produced by `@solana/kit`.

**Legacy message:**

| Part | Size | Content |
|---|---|---|
| header | 3 | `num_required_signatures`, `num_readonly_signed_accounts`, `num_readonly_unsigned_accounts` |
| account key count | compact-u16 | one byte for values below 128 |
| account keys | 32 each | ordered: writable signers, read-only signers, writable non-signers, read-only non-signers |
| recent blockhash | 32 | |
| instruction count | compact-u16 | |
| instructions | variable | each: `program_id_index` (1), account count (compact-u16), account indices (1 each), data length (compact-u16), data |

**Version 0 message:** one prefix byte `0x80` (bit 7 set, version in the low 7 bits), then the same fields as a legacy message, then a vector of address-table lookups (a compact-u16 count followed by the lookups). A v0 message that uses no lookup tables ends with the single byte `0x00`.

**The one instruction we accept**, SPL Token `TransferChecked` (source: [`solana-program/token` instruction definitions](https://github.com/solana-program/token/blob/main/interface/src/instruction.rs)):

| Field | Value |
|---|---|
| Program | the classic Token program, `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` |
| Data (10 bytes) | `u8` tag `12` · `u64` little-endian amount · `u8` decimals |
| Accounts | 0 source (writable) · 1 mint (read-only) · 2 destination (writable) · 3 owner (signer) |

With one signer who is also the fee payer, five keys and two read-only non-signers, the positions are forced: index 0 is the signer, indices 1–2 are the two writable token accounts, indices 3–4 are the mint and the Token program. Within each pair the order is whatever the transaction compiler chose: `@solana/kit` sorts by a collation of the base58 text, our own builder by raw key bytes, and the two do not always agree. The decoder therefore uses the instruction's indices, never fixed positions.

The same bytes are in [`../reference/code/vectors.json`](../reference/code/vectors.json) (`tx.legacy_1000.messageHex`) and [`../reference/code/vectors.h`](../reference/code/vectors.h) (`V_LEGACY`).

| Recipient wallet | `Gn2GQYmcQkatE2594ov2ELKkYWZHwARG7FiAoPWSEcxq` (the "Merchant" stand-in key); it does not appear in the message |

Things to notice:

- The destination comes **before** the source in the key list: kit sorted `2awX…` (bytes `178d…`) ahead of `Czgp…` (bytes `b237…`). For this key set kit's base58-text order and raw-byte order agree. A decoder that assumed "key[1] is the source" would swap them.
- The recipient's wallet key is nowhere in the message. Only its token account is. That is why the approval screen needs a hint plus an on-badge ATA derivation to name the recipient ([Policy checks](signing-gate.md#policy-checks), check 12).
- The amount is at offset 205 and the decimals at 213. `1000` with 2 decimals is shown as `10.00`.

A second kit-built vector, `tx.legacy_alt_order` (`V_ALT_LEGACY`), is the same kind of transfer for another key set: owner `CiGJCnuJg23Xb6Tn6eBecnqghAZmHzKbZWBNu6VDQxj7`, mint `Fr761VXmBpKsvLb7MB7j1pZ9H8Jtxa1Ua4fyVDossphm`. There kit's key order after the payer is `F8X8…Jr4` (destination), `ZXz7…h7o` (source), `Fr76…phm` (mint), `Token…5DA`, which is the opposite of raw-byte order in both pairs. The decoder accepts it like the first.

The **v0** form of the same transfer is 216 bytes: `0x80`, then the 214 bytes above (every offset moves up by one), then `0x00` for zero address-table lookups. The wire transactions are 279 bytes (legacy) and 281 bytes (v0): `0x01`, a 64-byte signature, then the message.

## Rules

Input: message bytes, length ≤ 256 (`SOL_TX_MSG_MAX`). The decoder accepts only a message that passes every step; the first violation returns the error named.

| Step | Rule | Error on violation |
|---|---|---|
| 1 | If bit 7 of byte 0 is set, the low 7 bits must be 0 (v0); skip that byte. Otherwise legacy. | `version` |
| 2 | Header: `num_required_signatures == 1`, `num_readonly_signed == 0`. | `header` |
| 3 | Account-key count byte `== 5` and `num_readonly_unsigned == 2`. (Only the one-byte compact-u16 form is accepted.) | `accounts` |
| 4 | 5 × 32 key bytes, 32 blockhash bytes present. | `truncated` |
| 5 | Instruction count byte `== 1`. | `ix_count` |
| 6 | `program_id_index < 5` and that key equals the Token program `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`. | `program` |
| 7 | Instruction account count byte `== 4`; every index `< 5`. | `ix_accounts` |
| 8 | Data length byte `== 10`; `data[0] == 12`. | `ix_data` |
| 9 | v0 only: address-table-lookup count byte `== 0`. | `lookups` |
| 10 | No bytes remain. | `trailing` |
| 11 | Authority (4th instruction account) is index 0. | `authority` |
| 12 | Source and destination are indices 1 and 2 in either order and differ; mint and program are indices 3 and 4 and differ. | `roles` |
| 13 | `amount` (u64 LE at `data[1..9]`) `> 0`. `decimals = data[9]`. | `amount_zero` |

Two more errors come from the bounds checks around these steps: `too_long` when the input is longer than 256 bytes, and `truncated` whenever the message ends before a field that a step needs (not only in step 4).

Outputs (`sol_transfer_t`): `fee_payer` (= authority), `source`, `mint`, `destination`, `blockhash`, `amount`, `decimals`, `version` (`0xFF` legacy, `0` v0).

Why each rule is there:

- **Steps 2 and 11: exactly one signer, and it is the authority.** The badge has one key. A message that needs a second signature is not something this badge alone is paying for, and one where the signer is not the transfer authority is not a transfer from the signer.
- **Step 3: exactly five keys.** Five is the number a single `TransferChecked` needs. Any additional program, account or lookup shows up as a different count and is refused before its meaning has to be understood.
- **Step 3: the one-byte count form only.** Compact-u16 allows the value 5 to be written in more than one way; accepting only the canonical single byte means one message has one parse.
- **Step 6: the classic Token program by its full 32-byte key.** A program is identified by its key, not by its position or its instruction layout. Token-2022 uses the same instruction layout and a different key, and is refused here.
- **Steps 7, 8: exact counts.** Four accounts is the single-owner form. More would be the multisig form, with extra signers the screen does not show.
- **Steps 9, 10: nothing after the instruction.** Lookup tables would bring in accounts that are not in the message, so the badge could not show them. Trailing bytes would be signed but not displayed.
- **Step 12: roles match the header.** Source and destination must be the writable accounts and must differ; the mint and the program must be the read-only ones and must differ. This rules out aliasing, where one key plays two roles.
- **Step 13: a zero amount is refused** because it has no legitimate use from this wallet and would show as `0.00`.

### What common transactions fail on

Derived from the rule order; the first failing step is what `reason:` shows on the [blocked screen](screens.md#screen-e).

| Transaction | First failing step | `reason:` |
|---|---|---|
| `TransferChecked` with a ComputeBudget `SetComputeUnitPrice` instruction added (258 bytes, vector `V_CB_LEGACY`) | the length check before step 1 | `too_long` (host-tested) |
| `TransferChecked` with a Memo instruction added | the length check when the memo is 8 bytes or longer (the message then exceeds 256 bytes); otherwise 3 (six keys) | `too_long` or `accounts` |
| Create-ATA plus `TransferChecked` (eight keys, over 256 bytes) | the length check before step 1 | `too_long` |
| Any message of at most 256 bytes with six account keys | 3 | `accounts` (host-tested) |
| Plain SPL `Transfer` (tag 3, no mint account) | 3 (four keys) | `accounts` |
| Token-2022 `TransferChecked` | 6 (other program key) | `program` |
| A transfer where the fee payer is not the token owner (two signers) | 2 | `header` |
| Multisig `TransferChecked` | 2 or 7 | `header` or `ix_accounts` |
| v0 message with an address lookup table | 3 or 9 | `accounts` or `lookups` |
| The same message with one byte appended | 10 | `trailing` |
| A `pay-req:` / `pay-proof:` / `pay-rcpt:` string | 2 (`0x70` is not 1) | `header` |

## Why extra instructions are refused

The decoder is an allowlist of one, by design [OURS]. It would be easy to "skip instructions we do not understand" and show the transfer; that is exactly blind signing, because the signature covers the skipped instructions too. Specifically:

- **`ComputeBudget::SetComputeUnitPrice`** lets whoever built the transaction set the priority fee, and so can spend the badge's SOL. The screen shows a HACK amount; it has no row for a fee.
- **Memo** can carry text that contradicts the screen, and it would be signed by the badge key.
- **ATA-create** spends rent from the payer and is unnecessary: every badge's token account is created before the event.
- **Token-2022** transfers can invoke transfer hooks and charge transfer fees that the screen cannot show.

The badge builds its own payments without any of these ([Transaction building](../protocol/transaction-building.md)), so refusing them costs nothing in the normal flow. The product is explicitly not a general-purpose wallet.

### Why the amount on screen is the amount that moves

`TransferChecked` carries the token's decimals in the instruction, and the Token program fails the instruction on chain unless that value equals the mint's real decimals (external fact; source above). So `amount / 10^decimals`, computed from the message, is what the Token program will transfer, or the transaction fails and nothing moves. The plain `Transfer` instruction has no such check, which is one more reason it is refused. The gate additionally requires the instruction's decimals to equal the configured decimals (policy check 8), so the number of decimal places on screen is also the one the user expects for HACK.

## sol_tx.c

`src/wallet/sol_tx.c`, in full. File: [`../reference/code/sol_tx.c`](../reference/code/sol_tx.c); its header is [`sol.h`](../reference/code/sol.h), listed in [Wallet C API](api.md#solh). Pure C99, no heap, no Arduino dependency. [OURS] host-tested.

```c
#include "sol.h"
#include <string.h>

typedef struct { const uint8_t *p; size_t n, at; } cur_t;
static int take(cur_t *c, size_t k, const uint8_t **out) {
  if (c->n - c->at < k) return -1;
  *out = c->p + c->at; c->at += k; return 0;
}
static int byte(cur_t *c, uint8_t *b) { const uint8_t *p; if (take(c, 1, &p)) return -1; *b = *p; return 0; }

sol_tx_err_t sol_tx_decode_transfer(const uint8_t *msg, size_t len, sol_transfer_t *out) {
  cur_t c; const uint8_t *keys, *bh, *idx, *data; uint8_t b, nro_unsigned, prog, i;
  uint8_t src, mint, dst, auth;
  if (len > SOL_TX_MSG_MAX) return SOL_TX_ERR_TOO_LONG;
  if (len < 1) return SOL_TX_ERR_TRUNCATED;
  c.p = msg; c.n = len; c.at = 0;
  memset(out, 0, sizeof *out);
  out->version = 0xFF;
  if (msg[0] & 0x80) {                                  /* versioned message prefix */
    if ((msg[0] & 0x7F) != 0) return SOL_TX_ERR_VERSION;
    out->version = 0; c.at = 1;
  }
  /* header: num_required_signatures, num_readonly_signed, num_readonly_unsigned */
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 1) return SOL_TX_ERR_HEADER;
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 0) return SOL_TX_ERR_HEADER;
  if (byte(&c, &nro_unsigned)) return SOL_TX_ERR_TRUNCATED;
  /* account keys: compact-u16 count. Only the single-byte encoding of 5 is accepted. */
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 5 || nro_unsigned != 2) return SOL_TX_ERR_ACCOUNTS;
  if (take(&c, 5 * 32, &keys)) return SOL_TX_ERR_TRUNCATED;
  if (take(&c, 32, &bh)) return SOL_TX_ERR_TRUNCATED;
  /* instructions */
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 1) return SOL_TX_ERR_IX_COUNT;
  if (byte(&c, &prog)) return SOL_TX_ERR_TRUNCATED;
  if (prog >= 5 || memcmp(keys + 32 * prog, SOL_TOKEN_PROGRAM_ID, 32) != 0) return SOL_TX_ERR_PROGRAM;
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 4) return SOL_TX_ERR_IX_ACCOUNTS;
  if (take(&c, 4, &idx)) return SOL_TX_ERR_TRUNCATED;
  for (i = 0; i < 4; i++) if (idx[i] >= 5) return SOL_TX_ERR_IX_ACCOUNTS;
  if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
  if (b != 10) return SOL_TX_ERR_IX_DATA;
  if (take(&c, 10, &data)) return SOL_TX_ERR_TRUNCATED;
  if (data[0] != 12) return SOL_TX_ERR_IX_DATA;         /* 12 = TransferChecked */
  if (out->version == 0) {                              /* v0: address table lookups must be empty */
    if (byte(&c, &b)) return SOL_TX_ERR_TRUNCATED;
    if (b != 0) return SOL_TX_ERR_LOOKUPS;
  }
  if (c.at != c.n) return SOL_TX_ERR_TRAILING;
  /* TransferChecked accounts: 0 source (w), 1 mint (r), 2 destination (w), 3 authority (signer) */
  src = idx[0]; mint = idx[1]; dst = idx[2]; auth = idx[3];
  if (auth != 0) return SOL_TX_ERR_AUTHORITY;
  /* With 5 keys, 1 signer and 2 readonly-unsigned: index 0 signer, 1-2 writable, 3-4 readonly. */
  if (src < 1 || src > 2 || dst < 1 || dst > 2 || src == dst) return SOL_TX_ERR_ROLES;
  if (mint < 3 || prog < 3 || mint == prog) return SOL_TX_ERR_ROLES;
  memcpy(out->fee_payer, keys, 32);
  memcpy(out->source, keys + 32 * src, 32);
  memcpy(out->mint, keys + 32 * mint, 32);
  memcpy(out->destination, keys + 32 * dst, 32);
  memcpy(out->blockhash, bh, 32);
  out->amount = 0;
  for (i = 0; i < 8; i++) out->amount |= (uint64_t)data[1 + i] << (8 * i);
  out->decimals = data[9];
  if (out->amount == 0) return SOL_TX_ERR_AMOUNT_ZERO;
  return SOL_TX_OK;
}

const char *sol_tx_err_name(sol_tx_err_t e) {
  static const char *const N[] = {"ok", "too_long", "truncated", "version", "header", "accounts", "lookups",
    "ix_count", "program", "ix_accounts", "ix_data", "authority", "roles", "amount_zero", "trailing"};
  return (unsigned)e < sizeof N / sizeof N[0] ? N[e] : "?";
}

size_t sol_tx_build_transfer(const uint8_t payer[32], const uint8_t source[32],
                             const uint8_t destination[32], const uint8_t mint[32],
                             const uint8_t blockhash[32], uint64_t amount, uint8_t decimals,
                             uint8_t *out, size_t cap) {
  const int src_first = memcmp(source, destination, 32) < 0;
  const int mint_first = memcmp(mint, SOL_TOKEN_PROGRAM_ID, 32) < 0;
  uint8_t *p = out; int i;
  if (cap < 214 || memcmp(source, destination, 32) == 0) return 0;
  *p++ = 1; *p++ = 0; *p++ = 2;                         /* header */
  *p++ = 5;                                             /* account keys */
  memcpy(p, payer, 32); p += 32;
  memcpy(p, src_first ? source : destination, 32); p += 32;
  memcpy(p, src_first ? destination : source, 32); p += 32;
  memcpy(p, mint_first ? mint : SOL_TOKEN_PROGRAM_ID, 32); p += 32;
  memcpy(p, mint_first ? SOL_TOKEN_PROGRAM_ID : mint, 32); p += 32;
  memcpy(p, blockhash, 32); p += 32;
  *p++ = 1;                                             /* one instruction */
  *p++ = (uint8_t)(mint_first ? 4 : 3);                 /* program id index */
  *p++ = 4;
  *p++ = (uint8_t)(src_first ? 1 : 2);                  /* source */
  *p++ = (uint8_t)(mint_first ? 3 : 4);                 /* mint */
  *p++ = (uint8_t)(src_first ? 2 : 1);                  /* destination */
  *p++ = 0;                                             /* authority = payer */
  *p++ = 10;
  *p++ = 12;                                            /* TransferChecked */
  for (i = 0; i < 8; i++) *p++ = (uint8_t)(amount >> (8 * i));
  *p++ = decimals;
  return (size_t)(p - out);
}

size_t sol_format_amount(uint64_t raw, uint8_t decimals, char *out, size_t cap) {
  char digits[21]; size_t n = 0, i, w = 0, int_len;
  if (decimals > 19) return 0;
  do { digits[n++] = (char)('0' + raw % 10); raw /= 10; } while (raw);
  while (n <= decimals) digits[n++] = '0';              /* at least one integer digit */
  int_len = n - decimals;
  if (int_len + (decimals ? 1 + decimals : 0) + 1 > cap) return 0;
  for (i = 0; i < int_len; i++) out[w++] = digits[n - 1 - i];
  if (decimals) { out[w++] = '.'; for (i = 0; i < decimals; i++) out[w++] = digits[decimals - 1 - i]; }
  out[w] = '\0';
  return w;
}

int sol_parse_amount(const char *text, uint8_t decimals, uint64_t *raw) {
  uint64_t v = 0; int seen_digit = 0, frac = -1; const char *s;
  for (s = text; *s; s++) {
    if (*s == '.') { if (frac >= 0) return -1; frac = 0; continue; }
    if (*s < '0' || *s > '9') return -1;
    if (frac >= 0 && ++frac > (int)decimals) return -1;
    if (v > (UINT64_MAX - (uint64_t)(*s - '0')) / 10) return -1;
    v = v * 10 + (uint64_t)(*s - '0'); seen_digit = 1;
  }
  if (!seen_digit) return -1;
  for (frac = frac < 0 ? 0 : frac; frac < (int)decimals; frac++) {
    if (v > UINT64_MAX / 10) return -1;
    v *= 10;
  }
  *raw = v;
  return 0;
}
```

Notes on the code:

- `cur_t` is a bounds-checked cursor. `take()` compares against the remaining length before advancing, so no read can pass the end of the buffer; `len` is at most 256, so the arithmetic cannot overflow.
- `sol_tx_decode_transfer` writes the key, blockhash and amount fields only after every structural check has passed. On any error, do not use `*out`.
- `sol_tx_build_transfer` orders the two token accounts, and the mint and Token program, by raw bytes. The result is always a valid message that the decoder accepts and that decodes to the inputs. It equals `@solana/kit`'s bytes when kit's base58-text order coincides with raw-byte order (vector `V_LEGACY`) and differs otherwise (vector `V_ALT_LEGACY`: same transfer, different key order, both decode to the same fields). Order inside a role class has no effect on chain. The builder is deliberately not made to imitate kit: kit uses a locale collation of base58 text, and reproducing that on the badge would buy nothing. It returns 0 when the buffer is smaller than 214 bytes or when source and destination are the same account.
- `sol_format_amount` and `sol_parse_amount` use integer arithmetic only. No float touches an amount anywhere in the wallet core.
- The builder exists for apps (`badge.sol.transfer_message`). Its output gets no special treatment: the gate decodes it again from scratch like any other bytes.

## Error names

`sol_tx_err_name()` returns these strings. They appear as `reason:` on the blocked screen and as the third return value (`detail`) of `badge.identity.sign` and `badge.identity.decode` in Lua.

| Value | Enum | Name | Rule |
|---|---|---|---|
| 0 | `SOL_TX_OK` | `ok` | accepted |
| 1 | `SOL_TX_ERR_TOO_LONG` | `too_long` | `len > SOL_TX_MSG_MAX` (256) |
| 2 | `SOL_TX_ERR_TRUNCATED` | `truncated` | ran out of bytes (step 4 and every other read) |
| 3 | `SOL_TX_ERR_VERSION` | `version` | step 1: versioned message with version ≠ 0 |
| 4 | `SOL_TX_ERR_HEADER` | `header` | step 2 |
| 5 | `SOL_TX_ERR_ACCOUNTS` | `accounts` | step 3 |
| 6 | `SOL_TX_ERR_LOOKUPS` | `lookups` | step 9 |
| 7 | `SOL_TX_ERR_IX_COUNT` | `ix_count` | step 5 |
| 8 | `SOL_TX_ERR_PROGRAM` | `program` | step 6 |
| 9 | `SOL_TX_ERR_IX_ACCOUNTS` | `ix_accounts` | step 7 |
| 10 | `SOL_TX_ERR_IX_DATA` | `ix_data` | step 8 |
| 11 | `SOL_TX_ERR_AUTHORITY` | `authority` | step 11 |
| 12 | `SOL_TX_ERR_ROLES` | `roles` | step 12 |
| 13 | `SOL_TX_ERR_AMOUNT_ZERO` | `amount_zero` | step 13 |
| 14 | `SOL_TX_ERR_TRAILING` | `trailing` | step 10 |

Every decoder error maps to one wallet error, `BADGE_ERR_UNKNOWN_INSTRUCTION` (`unknown_instruction`, headline `Unknown instruction`). The decoder name is the detail. See [Error codes](../reference/error-codes.md).

| Accept legacy | the 214-byte vector | `SOL_TX_OK`; `version == 0xFF`, `amount == 1000`, `decimals == 2`; payer, source, destination, mint and blockhash equal the vector's |

| Domain separation | the ASCII string `pay-req:` followed by 40 `x` characters | any error |

That is 15 negative decoder checks covering 14 kinds of rejection (the `program` error is checked twice). `ix_accounts` is the one decoder error with no negative check.

The same file tests amount formatting and parsing (`1000` ↔ `10.00`, `5` → `0.05`, `50000` → `500.00`, the full `u64` range, 9 decimals, and rejection of `1.234`, the empty string and `1e3` at 2 decimals), base58 in both directions, 24 curve-membership vectors and the ATA and attestation address derivations. A second test, `test_pay.c`, feeds the real signed byte strings of the payment protocol to this decoder and requires an error for each ([Message signing](signing-gate.md#message-signing)).

On-device acceptance for this requirement is T-F3 in [Acceptance](../testing/acceptance.md), with nothing signed in any of its three cases: a transfer whose instruction tag is 3 (`Transfer`) must show `Unknown instruction` with `reason: ix_data`; the 258-byte transfer with a ComputeBudget instruction (`tx.legacy_compute_budget` in `vectors.json`) must show `Unknown instruction` with `reason: too_long`; and a transfer of another mint must show `Unknown token` with `reason: unknown_mint`.

## Requirements covered

- **F3**: on-badge decoder for SPL Token `transferChecked`; anything else is "Unknown instruction" and blocked.
- **F2**: the amount, token and destination on the approval screen come from this decoder's output.
- Non-functional "Security: unknown instructions blocked, not blind-signed".
